# Правила разработки switch-lang

## Назначение и границы

- Проект — лёгкая утилита на Swift + AppKit для macOS на Apple Silicon (arm64), исправляющая слова, набранные в неверной раскладке RU ↔ EN.
- Цель, согласованные решения, сценарии и открытые вопросы описаны в [SPEC.md](SPEC.md). Читать его до изменения поведения.
- Согласованы macOS, русская ЙЦУКЕН ↔ английская QWERTY, автоматический режим и ручное исправление последнего введённого слова настраиваемой клавишей.
- Проектные предложения в спецификации не считать отдельным согласием пользователя. Существенные открытые вопросы решать до реализации затронутого поведения.
- Реализация разрешена пользователем. Целевой результат — приложение в строке меню macOS, ручной режим при первом запуске и назначение клавиши в настройках.
- Автоисправление запускается на всех разделителях слов; если действие уже отправило текст или сменило фокус, небезопасная замена пропускается.
- Использовать Swift из существующих Command Line Tools. Дополнительные инструменты, кеши и временные файлы размещать только внутри workspace в игнорируемом каталоге `.tools`; глобальную установку не менять.
- Работать в текущем workspace; не отменять чужие изменения. Отвечать кратко, на русском языке.

## Приоритеты

1. Сохранность текста и приватность пользователя.
2. Отсутствие заметной задержки при обычном наборе.
3. Минимальное потребление CPU и памяти в фоне.
4. Простота реализации и минимальное количество зависимостей.

При конфликте приоритетов лучше пропустить сомнительное исправление, чем изменить чужой текст или задержать ввод.

## Swift и архитектура

- Использовать Swift 6.4.2 в режиме языка Swift 5, AppKit и deployment target macOS 11.0; совместимость исполнения с macOS 11 проверять отдельно.
- Прикладная логика и системная интеграция — на Swift. Для неблокирующих 64-битных атомиков разрешён минимальный C11-адаптер без прикладной логики; новые внешние зависимости не добавлять без необходимости.
- Отделять чистое преобразование раскладки и определение кандидата от macOS-интеграции, настроек и интерфейса.
- Не создавать универсальные платформенные слои для ещё не запрошенных Windows и Linux.
- Предпочитать явные типы и владение ресурсами. Ограничивать размеры буферов и очередей; не хранить историю набора.
- Обработчик системных событий должен быть коротким: без дискового и сетевого I/O, ожидания интерфейса и длительных блокировок.
- Не добавлять опрос по таймеру там, где достаточно системного события. Не вводить асинхронный runtime без измеримой необходимости.
- Сокращать аллокации на пути ввода по результатам профилирования, а не ценой непроверяемого кода.
- Небезопасные указатели и приведения разрешены только при обоснованной необходимости на границе системного API. Изолировать их, проверять типы/границы и описывать инварианты в комментариях `SAFETY`.
- Не использовать принудительное извлечение Optional или `try!` для внешних данных и отказов системных API. Не сравнивать проверяемый AX-суффикс канонически эквивалентным `String ==`: нужны точные UTF-16 units. Ошибки не маскировать успешным результатом.
- Имена должны быть полными и однозначными. Не добавлять заглушки, неиспользуемые настройки и зависимости «на будущее».

## Приватность и интеграция

- Введённый текст не сохранять на диск, не включать в логи, отчёты об ошибках, телеметрию или сетевые запросы.
- Не собирать пользовательский набор для словаря или тестовых данных. Использовать синтетические примеры.
- Не обходить Secure Input и ограничения защищённых полей. Если безопасность контекста не подтверждена, исправление запрещено.
- При потере фокуса или достоверной позиции каретки сбрасывать кандидат на замену. Не редактировать текст по устаревшему буферу.
- Не подменять пользовательский буфер обмена ради вставки текста без отдельно согласованного контракта.
- Собственные синтетические события не должны запускать повторные исправления.
- Запрашивать только необходимые разрешения macOS и объяснять их пользователю. Возможности и ограничения API проверять по официальной документации и прототипом.

## Проверка изменений

- Перед правками читать относящиеся файлы и проверять `git status`. Изменения делать минимальными.
- Выполнять `scripts/test.sh`: строгий `swift-format`, Swift-сборку с warnings-as-errors, синтетические self-test/лог-тесты и проверки инструмента подписи. Release-сборку и read-only проверку таблиц выполнять отдельно. Исходная Rust/Objective-C реализация архивирована в `.tools/swift-migration-before` и не входит в активную сборку.
- Чистое преобразование проверять в обе стороны, включая регистр, Unicode и символы, не принадлежащие поддержанным раскладкам.
- Интеграцию проверять отдельно: смена фокуса, каретки и раскладки, защищённый ввод, конфликт клавиш, быстрый набор и собственные события.
- Производительность измерять в release-сборке на синтетическом вводе; указывать macOS, оборудование, сценарий и методику. Не выдавать предположение о скорости за замер.
- Для исправления дефекта сначала сохранять исходный сценарий и добавлять воспроизводящую проверку. Не подгонять ожидаемый результат под реализацию.
- После изменения поведения актуализировать связанную документацию. Отслеживаемые файлы перемещать через `git mv`.
- Перед завершением просматривать весь относящийся diff, включая новые файлы, и проверять Markdown.
- В отчёте различать реализованное, проверенное и непроверенное. Не заявлять поддержку приложений и версий macOS без проверки.
